# Deploying the Maximus backend (Render free + Neon Postgres)

This is a checklist for **you**. Nothing here has been run yet: the accounts do not exist. The repo is public, so
no secret ever goes in a file you commit; every secret is typed into the Render or GitHub dashboard.

Facts below were read from the providers' docs on 2026-11-25. Plans change: where a line says
**(not verified)** I could not confirm it, so check the provider's page before relying on it.

## 0. What you need

- A GitHub account (the repo is already there), a Neon account, a Render account.
- A Google Cloud project (for Google sign-in) and a Resend account (for emails).
- The PostgreSQL 16+ client tools on your PC (`pg_dump`, `pg_restore`, `psql`) for backups.

## 1. Neon (database)

1. neon.com, new project. Region: same continent as Render (`render.yaml` uses `frankfurt`; change both together).
   Postgres 16 or newer.
2. Connect dialog, copy **two** strings, both with `sslmode=require`:
   - **Pooled** (host contains `-pooler`): this is `DATABASE_URL`.
   - **Direct** (no `-pooler`): this is `DATABASE_URL_DIRECT` (migrations and backups only).
3. Keep both strings out of git, chat and screenshots. If one leaks, reset the role password in Neon.

Free plan limits (neon.com docs, read 2026-11-25): 1 GB storage per project, 100 compute hours per project a
month, compute **scales to zero after 5 minutes idle** (the first query after that takes about a second), and
only a **6-hour** restore window. That window is not a backup: see section 9.

## 2. Render (web service)

1. Render dashboard, New, **Blueprint**, pick this repo and branch. It reads `render.yaml` (service
   `maximus-api`, free plan, root directory `backend`).
2. When asked, fill the `sync: false` values (table in section 3). `JWT_SECRET` and `INSTALL_ID_SALT` are
   generated by Render; do not change them later (a new salt resets the abuse counters, a new JWT secret signs
   everyone out).
3. The **build command** installs requirements and runs `alembic upgrade head` against `DATABASE_URL_DIRECT`. A
   failed migration fails the deploy and the previous version keeps serving. Render's free plan has no
   pre-deploy command (paid only), which is why migrations run in the build. Run one instance, never several.
4. Render free web service: sleeps after 15 minutes without traffic, about one minute to wake, 750 free instance
   hours a month per workspace, and a disk that is wiped on every deploy, restart and wake-up.
5. Python is pinned with the `PYTHON_VERSION` env var in `render.yaml` (a full version, `3.12.8`; CI tests 3.12).
6. `autoDeploy` is off: use Manual Deploy after CI is green.

## 3. Environment variables

Render, the service, Environment. Names only; every name is explained in `backend/README.md` (Environment).

| Name | Where the value comes from |
|---|---|
| `ENVIRONMENT` | already `production` in `render.yaml` |
| `DATABASE_URL` | Neon pooled string (secret) |
| `DATABASE_URL_DIRECT` | Neon direct string (secret) |
| `JWT_SECRET`, `INSTALL_ID_SALT` | generated by Render |
| `APP_BASE_URL` | the service URL, `https://maximus-api.onrender.com` (no trailing slash). Email links use it |
| `GOOGLE_CLIENT_ID` | section 4 |
| `EMAIL_PROVIDER` | `resend` (already set) |
| `EMAIL_FROM` | a sender on your verified Resend domain, e.g. `Maximus <no-reply@yourdomain>` |
| `EMAIL_PROVIDER_API_KEY` | section 5 (secret) |
| `CONTACT_EMAIL` | shown on `/privacy` |
| `OPENROUTER_API_KEY`, `GEMINI_API_KEY` | chat providers (secrets); with neither, chat answers 503 `chat_resting` |
| `MEDIA_BASE_URL` | after you choose media storage (section 10); leave empty until then |

Production refuses to start if `JWT_SECRET` (32+ characters), `INSTALL_ID_SALT` or a Postgres `DATABASE_URL` is
missing, so a bad setup fails loudly in the deploy log.

## 4. Google sign-in

1. console.cloud.google.com, new project, APIs & Services, OAuth consent screen (External, app name Maximus, your
   support email, scopes `openid email profile`). Leave it in Testing while you try it; publish before launch.
2. Credentials, Create credentials, OAuth client ID, **Web application**. This id is `GOOGLE_CLIENT_ID` and the
   app's `serverClientId`. It is not a secret.
3. Credentials, another OAuth client ID, **Android**: the app's package name plus the SHA-1 of the signing key
   (debug key now, release or Play App Signing key later). Without it the Android sign-in dialog fails.

## 5. Email (Resend)

1. resend.com, add your domain and publish the DNS records it shows (SPF, DKIM) until it says verified. Without
   your own domain Resend may only send to your own address **(not verified)**: fine for a first test.
2. Create an API key with sending access only: `EMAIL_PROVIDER_API_KEY`. Set `EMAIL_FROM` to an address on that domain.
3. Free-plan send limits **(not verified)**: check resend.com/pricing; account emails are low volume.

## 6. First deploy and smoke tests

Deploy from the dashboard and wait for "Live". Replace the host; the first call may take a minute to wake it.

```
curl -i https://maximus-api.onrender.com/healthz
# 200 {"status":"ok","version":"..."} with X-Content-Type-Options and Strict-Transport-Security headers

curl -s https://maximus-api.onrender.com/v1/catalogue | head -c 300
# JSON; an empty list is normal until content is imported (section 7)

curl -i https://maximus-api.onrender.com/privacy
# 200 HTML page

curl -i https://maximus-api.onrender.com/docs
# 404: the API docs are hidden in production

curl -i -X POST https://maximus-api.onrender.com/v1/chat -H "Content-Type: application/json" -d "{}"
# 401 or 422, never 500
```

Then register a test account from the app, sign in, use "Forgot password" to check the reset mail arrives and its link opens, and delete the
account from Settings. In Render Logs there must be no traceback and no `token=` value (they are redacted).

## 7. Content

The database starts empty. Import titles from your PC against the **direct** URL (importer in `backend/ingest`,
see `backend/README.md`), with `DATABASE_URL=<direct url>` set for that one terminal only. Production serves
published titles only (`SERVE_DRAFTS=false`).

## 8. Daily purge

Render has **no free cron job** (cron jobs cost at least $1 a month each). So the purge runs from GitHub Actions
(`.github/workflows/purge.yml`, 03:17 UTC daily):

1. GitHub, repo, Settings, Secrets and variables, Actions, New repository **secret** `PURGE_DATABASE_URL` = the
   Neon **pooled** string. Secrets are not visible in a public repo or its logs.
2. Run the workflow once by hand (Actions, purge, Run workflow); it prints `removed: ...`.

Until the secret exists the job skips itself. A missed day loses nothing: chat purges lazily too. If you later pay
for Render, uncomment the cron block at the bottom of `render.yaml` and delete the workflow.

## 9. Backups

Neon's 6-hour window is not a backup. Run `backend/tools/backup.ps1` from **your own computer**:

```
powershell -ExecutionPolicy Bypass -File backend\tools\backup.ps1
```

- It runs `pg_dump --format=custom` against the **direct** URL (`DATABASE_URL_DIRECT` env var, or it asks with
  hidden input), checks the file reads back with `pg_restore --list`, writes
  `backend\backups\maximus-<UTC time>.dump` and deletes dumps older than 28 days. The folder is gitignored.
- **Never** upload a dump to GitHub, a GitHub Actions artifact, a release, an issue or any public place: this repo
  is public and the dump holds email addresses, password hashes, synced records and chat history. The script has
  no upload step, and a test fails if one is added. Keep dumps on your PC, optionally one encrypted copy on a
  private drive. The 28-day deletion also bounds how long a deleted account lives in backups; say so in the
  privacy policy.
- **How often:** weekly while there are only test users; **daily** once real users exist (the most you can lose
  is the gap between dumps). Use a calendar reminder or a Windows Task Scheduler task running the command, with
  `DATABASE_URL_DIRECT` set in your user environment.
- **Test a restore once** before launch: into an empty second Neon project or a local Postgres, run
  `pg_restore --no-owner --dbname <empty db url> <file>`, then `alembic current` against it.

## 10. Media (open decision, nothing implemented)

Problem: Render's free disk is wiped on every redeploy, restart and wake-up, so `backend/media/` served at
`/media` breaks. `app/main.py` mounts `/media` only if the folder exists, so on Render it just answers 404. Image
URLs are written by the ingest from `MEDIA_BASE_URL`, so the fix is a different base URL, not new server code.

| Option | Limits and cost | Notes |
|---|---|---|
| **Cloudflare R2** (recommended) | Free: 10 GB-month storage, 1 million write-class and 10 million read-class operations a month, no egress fees (developers.cloudflare.com/r2/pricing, read 2026-11-25). Beyond that about $0.015 per GB-month **(third-party figure, not verified)** | S3-compatible; upload from your PC after ingest. A public bucket needs a custom domain on Cloudflare for production; the free `r2.dev` URL is for testing and rate limited **(not verified)**. Whether a card is needed to enable R2 **(not verified)** |
| Bundle poster art in the app (CONTRACTS 18, 21), keep only lesson images in storage | App size grows; posters never need the network | Cuts storage to a few MB; combine with any option |
| Render Static Site (free, listed on render.com/docs/free) | Free static hosting; images must be committed to a repo | Wikimedia images are freely licensed, so a public repo is fine licence-wise, but it bloats git history and needs a deploy per image change |
| Neon | No object storage found in Neon's docs **(not verified)**; images as Postgres rows would eat the 1 GB limit | Not recommended |

Recommendation: **R2 for lesson images, plus bundled poster art.** Once chosen, set `MEDIA_BASE_URL`, re-run the
ingest so image URLs are rewritten, and record it in DECISIONS (D44).

## 11. Production hardening review

Fixed in this branch (tests in `backend/tests/test_hardening.py`):

- `/docs` and `/openapi.json` are not served in production (`/redoc` was already off).
- Every API response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY` and a `default-src 'none'` CSP; production adds `Strict-Transport-Security`. The HTML
  pages keep their own CSP.
- CORS: off unless `CORS_ORIGINS` is set (the Android app needs none); a `*` is ignored in production; allowed
  request headers are `Authorization`, `Content-Type` and `If-None-Match` instead of everything.
- Log redaction: uvicorn's access log wrote the `?token=...` of reset and delete links to Render's logs.
  The value is now replaced with `[redacted]`. Already true: chat text and passwords are never logged, and the
  DEV MAIL line with an address exists only for `EMAIL_PROVIDER=console`.

Not fixed, for you to decide:

1. **Cold start.** The first request after 15 idle minutes takes about a minute (Render) plus about a second for
   Neon to wake. The app needs a 60 s connect timeout for the first call and a "Waking the server..." state. The
   chat provider timeout (12 s) starts only once the server is awake. Do not ping the service to keep it awake:
   the free tier is meant to sleep, and `/healthz` deliberately does not touch the database.
2. **In-memory rate limits** are per process and reset on every wake-up: one worker only, as configured. They are
   a brake, not a wall; the per-account chat caps live in the database.
3. **`--forwarded-allow-ips="*"`** trusts `X-Forwarded-For` from any peer. Safe on Render (only its proxy reaches
   the process); do not reuse this command on a host that is directly reachable.
4. **No request-size cap at the proxy.** Chat and sync have their own limits in the app; the free tier has no
   body-size setting.
5. **No error monitoring or alerts.** Render's log viewer only; add Sentry or an uptime check if you want paging.
6. **Personal data in dumps and Neon history:** list Neon, Render, Resend and the chat providers as processors in
   the privacy policy.
7. **Render free bandwidth** is limited (the number is not on the docs page **(not verified)**); with no card on
   file Render suspends free services for the rest of the month when it runs out.
8. **Do not use Render's own free Postgres** (expires after 30 days, no backups); stay on Neon.
